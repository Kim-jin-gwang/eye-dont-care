# 데이터 파이프라인 작업 계획 (최종본)

작성: 데이터/백엔드 담당
아키텍처: 실시간 서빙 + 야간 배치(감사 + 분석)

---

## 확정 설계 원칙
- **서빙 = 실시간** (운영 DB 직접 조회). 컬럼이든 JSONB든 제출 즉시 저장되어 **모두 실시간**. 배치 mart로 서빙 전환은 **안 함**.
- **`participants_.score` 컬럼 승격** — 랭킹·전적처럼 **대량 정렬/집계하는 hot path** 성능용. (값 자체는 프론트가 계산해 제출)
- **`game_result` JSONB 유지** — 원본·상세·감사 소스. 게임별로 다른 부가값(콤보·라운드·골 등)과 미래 확장을 담는 유연한 그릇.
- **야간 배치(dbt) = 감사(reconcile) + 분석, 둘 다.** 서빙 경로엔 일절 안 들어감.
- **자동 교정 = "안전 백필"만**(예: score NULL 채우기), 나머지 불일치는 **리포트**(사람 검토).
- **오케스트레이션** = Airflow(파이프라인 역량/학습 목표) 또는 cron/`@Scheduled`(가볍게). 로직은 동일, 트리거만 교체 가능.

## 서빙 경로 (전부 실시간, 운영 DB 직접)
| 소비 | 읽는 곳 | 이유 |
| --- | --- | --- |
| 랭킹 · 전적 목록 | `participants_.score` / `outcome` 컬럼 | 대량 정렬 → 컬럼(인덱스) 성능 |
| 게임 결과 상세 | `game_result` JSONB | 한 건 조회 → JSONB 그대로 충분 |
- 랭킹 지표는 게임 무관 **단일 숫자(score)**, 에어하키만 `outcome=WIN` 카운트(집계가 COUNT라 다름).

## score에 들어가는 값 (프론트 계산 → 백엔드 적재)
| 게임 | score |
| --- | --- |
| BLINK 깜빡이 | 깜빡인 횟수 |
| EYEFIGHT 눈싸움 | 생존 초(정수) |
| RHYTHM 리듬 | 리듬 점수 |
| DRAWING 그림 | 3라운드 총점 |
| HOCKEY 에어하키 | 골 수(랭킹은 outcome 승수 사용, 골은 기록용) |

## 작업 순서
**Phase A — 서빙 정규화 (백엔드, 실시간)**
1. `participants_`에 `score`(nullable bigint) 컬럼 추가
2. 게임결과 제출 시 slot score 파싱 → `score` 저장 (JSONB도 그대로 저장)
3. 랭킹 서비스: `extractScore(JSONB)` → `participants_.score` 읽기로 리팩터
4. 테스트 갱신

**Phase B — 야간 배치 (dbt): 감사 + 분석 (둘 다)**
5. `fact_game_play` = JSONB에서 score 재계산(공통 재료)
6. **[감사]** `reconcile`: `score` 사본 vs 기대값 대조 → `data_quality_issues` 리포트 + 안전 백필(score NULL만) + 이상치 탐지
7. **[분석]** 분석 마트: 게임/유저/밸런스/랭킹히스토리/운영 지표
   - 게임: 플레이 수·시간대 분포·평균 점수 / 유저: DAU·리텐션 / 밸런스: 승률·성사율
   - 랭킹 히스토리(주간 스냅샷) / 이상 탐지(치팅 의심) / 관리자 대시보드 요약
8. dbt tests(데이터 품질)

**Phase C — 오케스트레이션**
9. 야간 잡: `재계산 → (감사: 대조·백필·리포트) + (분석: 마트) `, 멱등·스케줄. Airflow DAG 또는 cron.

## 명시적으로 "안 하는 것"
- 배치 mart 기반 **서빙** (지연 → 실시간 요구와 충돌)
- 랭킹 값 자체를 배치가 덮어쓰기 (랭킹은 파생 — 입력 score만 맞추면 됨)
- 애매한 불일치 **자동 수정** (사람 검토)
- Spark/Kafka/Hadoop (현재 규모엔 오버엔지니어링)
